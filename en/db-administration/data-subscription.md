# Real-time data push

KWDB provides the out-of-box real-time data push capabilities. It captures changes to key business data and DDL operations on time-series tables within the database, encapsulates such information into message objects in JSON format, and pushes them to Kafka Topics for downstream systems to retrieve and consume. KWDB allows creating data push pipelines for a single time-series database, a single time-series table, specified columns of a single time-series table, or multiple time-series tables.

::: warning Notes
When pushes messages to Kafka, if any message violates Kafka's constraints (e.g., the message size exceeds the default 1 MB limit), the system will throw an error and record the details in logs.:::

## How It Works

KWDB supports creating data push tasks via SQL statements to synchronize time-series data and DDL operations on time-series tables to Kafka topics in real time. Users can consume data from Kafka topics through Kafka clients and write the data to third-party message components or target databases.

![](../../static/db-administration/data-subscription-3.1.png)

- When a data push pipeline has been created for a time-series database
  - If the data push service is enabled, users are allowed to create, modify, and delete time-series tables. After such operations are performed, the system pushes the corresponding DDL statements to the message queue of the data push pipeline, restarts the data push service, and continues pushing data based on the latest table structure in the time-series database. The pushed data includes new data generated by `INSERT`、`DELETE` and `UPDATE` operations, as well as existing historical data in the time-series tables.
  - If the data push service is disabled, users are allowed to create, modify, and delete time-series tables. After the data push service is restarted, the system continues pushing data according to the latest table structure of the time-series database.


- When a data push pipeline has been created for a single time-series table
  - - If the data push service is enabled, users are allowed to modify and delete the time-series table. After table modification or deletion, the system pushes the corresponding DDL statements to the message queue of the data push pipeline, restarts the data push service, and continues pushing data based on the latest table structure, including new data generated byINSERT, DELETE, and UPDATE operations and existing historical data. If the target table is dropped or renamed, or any table column is removed, the system stops pushing data for the affected table or columns.
  - If the data push service is disabled, users are allowed to modify and delete the time-series table. After the service is restarted, data will be pushed based on the latest table structure. If the target table is dropped or renamed, or any table column is removed, the system stops pushing data for the affected table or columns.

- When a data push pipeline has been created for specified columns of a time-series table
  - If the data push service is enabled, users are allowed to modify and delete the time-series table. After table modification or deletion, the system pushes the corresponding DDL statements to the message queue of the data push pipeline, restarts the data push service, and continues pushing data based on the latest table structure, including new data generated by `INSERT`、`DELETE` and `UPDATE` operations and existing historical data. If the target table or its columns are renamed or dropped, the system stops pushing data for the affected table or columns.
  - If the data push service is disabled, users are allowed to modify and delete the time-series table. After the service is restarted, the system pushes data according to the latest table structure. If the target table or its columns are renamed or dropped, the system stops pushing data for the affected table or columns.

## Limitations

- KWDB does not support pushing data from relational tables.
- Filter conditions containing aggregate functions, type conversion, collation rules, system column references, or non-immutable built-in functions are not supported.
- When the push target is a single database or multiple time-series tables, column specification and filter conditions are not supported, and push objects cannot be modified.
- If columns specified in filter conditions are deleted or renamed, the data push service will fail to run. In this case, users shall modify the filter conditions and restart the data push service.
- KWDB does not support applying data deduplication rules during real-time data push.
- Historical data may be omitted,if the data is not generated in real scenarios or is out-of-order with a large time deviation.
- In a cluster high-availability environment, table operations related to CDC on newly expanded nodes will be blocked before the new nodes establish connections with business services.

## Main Features

- Data Push Objects
  - KWDB supports pushing data from a single time-series database, a single time-series table, specified columns of a single time-series table, or multiple time-series tables.
  - The WITH keyword is supported to configure data push parameters.
  - For single-table data push, the WHERE clause is supported to create data push tasks with custom filter conditions.
- Data Sources
  - Real-time data: After a data push task is enabled, the system pushes data written, deleted, or updated via INSERT, DELETE, and UPDATE statements, as well as DDL operations performed on the source database.
  - Historical data
    - Out-of-order data inserted into the database.
    - Existing data in the database before the data push task is enabled. Such data will be pushed in batches after task startup. Historical DDL operations generated on the source side are not supported.
    - Data changes (via `INSERT`、`DELETE`、`UPDATE`) and DDL operations performed on the source side during the suspension of the data push task.
    - Data imported through IMPORT and INSERT INTO ... SELECT statements.

    ::: warning Notes
    Database-level import is not supported for data push.
    :::

- Supported SQL Operations：`INSERT`、`DELETE`、`UPDATE`、DDL statements.

    ::: warning Notes

    - Currently, KWDB only supports data deletion and Tag value updates based on the Primary Tag.
    - After enabling data push, an interval of at least 4 seconds is recommended between consecutive DDL operations.
    - If a `DELETE` or `UPDATE` operation affects zero rows, no data push will be triggered.

    :::

  - `DELETE`：Supports pushing `DELETE` operations on data columns and ordinary Tag columns. All real-time delete operations on the source side will be pushed to the target immediately during task execution. Deletion operations occurring during task suspension will be pushed after task resumption to ensure data consistency between the source and target.
  - `UPDATE`：Supports pushing  `UPDATE` operations on data columns and ordinary Tag columns. For data columns with deduplication policies configured on the target side, updates will be processed with deduplication at the target end. All real-time update operations on the source side will be pushed immediately during task execution. Updates occurring during task suspension will be pushed after task resumption to ensure data consistency.

- Data Filtering Rules：For single-table data push, simple row-level conditional filtering is supported for real-time data synchronization, including:
  - Filtering on data columns, Primary Tag columns, and ordinary Tag columns.
  - Filtering based on timestamp columns of time-series tables.
- Data Push Configuration
  - KWDB asynchronously pushes time-series data in JSON format to specified Kafka topics. If an invalid push target is specified, the system will return an error message after a push attempt. The following shows a Kafka connection example:

    ```bash
    kafka://{kafka_cluster_address}:{port}?topic_name={topic_name}&tls_enabled=true&ca_cert={ca_cert}&sasl_enabled=true&sasl_user={sasl_user}&sasl_password={sasl_password}
    ```

    - `kafka_cluster_address`：IP address of the Kafka cluster.
    - `port`： Port number. The default value is `9093`.
    - `topic_name`：Name of the target Kafka topic for data push.
    - Kafka authentication modes and related parameters
      - `tls_enabled`：Set to `true` to enable TLS connection with Kafka. This parameter must be used together with `ca_cert`.
      - `ca_cert`: Base64-encoded CA certificate for Kafka TLS authentication. Note: You can encode the CA certificate by running the command `base64 -w 0 ca.cert`.
      - `client_cert`：Base64-encoded PEM certificate, which must be used with `client_key`.
      - `client_key`：Base64-encoded private key of the PEM certificate, which must be used with client_cert.
      - `sasl_enabled`：Set to true to adopt the SASL/PLAIN authentication protocol. Both `sasl_user` and `sasl_password` are mandatory in this case.
      - `sasl_user`：SASL username.
      - `sasl_password`：SASL password.

  - Currently, KWDB only supports pushing single or multiple records in JSON format. Below is a message example:
    - Regular data push message (message type: `insert`)

        ```json
        {
          "change": [
            {
              "kind": "insert",
              "database": "benchmark",
              "schema": "public",
              "table": "cpu",
              "columnnames": ["k_timestamp", "hostname", "max_usage_user" ],
              "columntypes": [ "integer", "text", "integer" ],
              "columnvalues": [
                [ 173441827100000, "www.example1.com", 77],
                [ 173441827200000, "www.example1.com", 80],
                [ 173441827300000, "www.example1.com", 65]
              ]
            }
          ]
        }
        ```

    - Restart catch-up data message (message type: `snapshot`)

        ```json
        {
          "change": [
            {
              "kind": "snapshot",
              "database": "benchmark",
              "schema": "public",
              "table": "cpu",
              "columnnames": ["k_timestamp", "hostname", "max_usage_user" ],
              "columntypes": [ "integer", "text", "integer" ],
              "columnvalues": [
                [ 173441827100000, "www.example1.com", 77],
                [ 173441827200000, "www.example1.com", 80],
                [ 173441827300000, "www.example1.com", 65]
              ],
            }
          ]
        }
        ```

    - Delete operation message.

        ```json
        {
          "change": [
            {
              "kind": "delete",
              "database": "benchmark",
              "schema": "public",
              "table": "table2",
              "statement": "DELETE FROM benchmark.public.table2 WHERE time > '2023-05-01 10:00:00';"
            }
          ]
        }
        ```

    - Update operation message.

        ```json
        {
          "change": [
            {
              "kind": "update", 
              "database": "benchmark",
              "schema": "public",
              "table": "table1",
              "statement": "UPDATE benchmark.public.table1 SET tag3 = true WHERE tag1 = 1 AND tag2 =1;"
            }
          ]
        }
        ```

    - DDL operation message. DDL types are distinguished by the `kind` field. Supported values include `create_table`, `alter_table` and `drop_table`.

        ```json
        {
          "change": [
            {
              "kind": "create_table",
              "database": "benchmark",
              "schema": "public",
              "table": "tb1",
              "statement":"CREATE TABLE benchmark.public.tb1(k_timestamp TIMESTAMPTZ NOT NULL, ml FLOAT) TAGS (id INT NOT NULL, type VARCHAR(30) NOT NULL) PRIMARY TAGS (id);"
            }
          ]
        }
        ```

  - Users can configure the global maximum number of data push failures. Once the number of failures exceeds the configured threshold, the system stops pushing data. Use the command `SET CLUSTER SETTING ts.pipe.sink_max_retries` to adjust the maximum retry count. The default value is 5.
  - The `buffer_size` parameter allows per-task configuration of immediate data push. A value of 0 enables immediate push.
  - The `ignore_history` parameter controls whether historical data is pushed. If historical data push is enabled after the real-time push service starts, the system first queries and synchronizes all existing historical data, then automatically captures and pushes subsequent data updates.
  - The `retrieve_tags` parameter enables supplementary filling of ordinary tags
     - If ordinary tags are not specified in the output or filter columns of the push task, no tag supplementation occurs regardless of this setting.
     - When retrieve_tags is enabled: if ordinary tags are specified in output or filter columns but missing in newly written records, the system automatically supplements the corresponding ordinary tag values. If the newly written Primary Tag and ordinary tag combination mismatches the initial record, the system corrects the ordinary tag value to the first recorded value before filtering and pushing the data.
     - When retrieve_tags is disabled: missing ordinary tag values in new records are treated as NULL. If the tag combination differs from the initial record, the system uses the newly written ordinary tag value for filtering and pushing.

- Resumable Transmission
    If the data push service is stopped and restarted later, a large amount of data may have been written to the database during the offline period and not pushed to the target. Such data is regarded as unpushed data.
During real-time data pushing, KWDB uses the ingestion OSN (ordered sequence number) of time-series data as the replication checkpoint to record push progress. When restarting the service, the system identifies the range and volume of unpushed data based on the checkpoint. If historical data push is enabled, the system synchronizes all historical data first, then continues pushing real-time incremental data. 

    ::: warning Notes

    - The resumable transmission mechanism synchronizes the final state of source data rather than the full sequence of historical operations.
    - The default replication checkpoint timestamp is `1970-01-01`. The configurable time range is `1970-01-01 00:00:00 – 2262-01-01 00:00:00`(UTC).

    :::

- High Availability
  - If a node in the running push cluster fails, restarts, or scales, the system automatically recovers data push tasks and resumes pushing data from the last recorded replication checkpoint.
- Data Push Task Management
  - Supports starting and stopping data push services.
  - Supports resuming unpushed data from the breakpoint after service restart.
  - Supports viewing running push task details, including task name, push content, creation time, creator, current status, start time, end time, failure time, and failure causes.
  - Supports deleting specified data push tasks. If a batch push is in progress, the task stops or is deleted after the current batch completes.<br >
For more details about task management, see [Data Pipe](../sql-reference/other-sql-statements/pipe-sql.md).
